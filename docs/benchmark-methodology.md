# Методология API-бенчмарка AB Platform

Документ описывает локальный dev-бенчмарк API AB Platform. Его цель — не доказать production SLA, а получить воспроизводимую инженерную оценку базовых endpoint платформы в одинаковых условиях стенда.

## 1. Цель бенчмарка

Бенчмарк нужен для проверки трех свойств:

1. Публичный SDK endpoint быстро отдает активные конфигурации экспериментов.
2. Событийный endpoint принимает batched-события без ошибок и с приемлемой задержкой.
3. Административный analytics endpoint способен агрегировать накопленные события и возвращать базовые метрики.

Результаты используются как дополнительное подтверждение инженерной достаточности платформы: система не только функционально работает, но и выдерживает небольшой контролируемый поток запросов в локальном окружении разработки.

## 2. Проверяемые endpoint

В бенчмарке используются следующие HTTP endpoint:

1. `GET /sdk/experiments/active?appId=...` — получение активных экспериментов для SDK.
2. `POST /sdk/events/batch` — прием пачки событий от SDK.
3. `GET /admin/analytics/feature-toggles/:experimentKey?appId=...` — получение агрегированной аналитики по выбранному тогглу.

Первый и второй endpoint относятся к публичному SDK-контуру. Третий endpoint относится к административному контуру и требует JWT администратора.

## 3. Метрики

Скрипт считает следующие показатели:

1. `requests` — количество выполненных запросов.
2. `statuses` — распределение HTTP-статусов ответа.
3. `avg latency` — средняя задержка запроса в миллисекундах.
4. `p50 latency` — медианная задержка: 50% запросов были не медленнее этого значения.
5. `p95 latency` — 95-й перцентиль: 95% запросов были не медленнее этого значения.
6. `p99 latency` — 99-й перцентиль: 99% запросов были не медленнее этого значения.
7. `throughput` — приблизительная пропускная способность в запросах в секунду.

Перцентили важны потому, что среднее значение может скрывать редкие медленные запросы. Для оценки пользовательского и эксплуатационного поведения полезно смотреть не только `avg`, но и `p95`/`p99`.

## 4. Запуск

Базовый запуск выполняется из корня монорепозитория:

```bash
pnpm bench:api
```

Пример запуска с явными параметрами:

```bash
pnpm bench:api -- --base-url=http://localhost:3000 --app-id=demo-app --requests=1000 --concurrency=30 --batch-size=20
```

## 5. Параметры

Скрипт поддерживает параметры командной строки:

1. `--base-url` — адрес backend, по умолчанию `http://localhost:3000`.
2. `--app-id` — идентификатор приложения, по умолчанию `demo-app`.
3. `--requests` — число запросов на каждый проверяемый endpoint, по умолчанию `1000`.
4. `--concurrency` — число параллельных воркеров, по умолчанию `30`.
5. `--batch-size` — количество событий в одном запросе `/sdk/events/batch`, по умолчанию `20`.

Также можно использовать переменные окружения:

1. `BENCH_BASE_URL`
2. `BENCH_APP_ID`
3. `BENCH_REQUESTS`
4. `BENCH_CONCURRENCY`
5. `BENCH_BATCH_SIZE`
6. `BENCH_ADMIN_EMAIL`
7. `BENCH_ADMIN_PASSWORD`

## 6. Подготовка стенда

Перед запуском должны быть доступны:

1. backend AB Platform;
2. PostgreSQL;
3. ClickHouse;
4. активный эксперимент для выбранного `appId`, если нужно бенчмаркать реальный analytics endpoint;
5. учетные данные администратора для проверки административной аналитики.

Если авторизация администратора не выполнена, скрипт пропускает проверку analytics endpoint и явно сообщает об этом в выводе.

## 7. События, создаваемые бенчмарком

Для проверки `/sdk/events/batch` скрипт отправляет синтетические события типа `impression`. Они имеют:

1. `event_id` с префиксом `bench-`;
2. `subject_key` с тестовым префиксом;
3. `variant_key = "A"`;
4. `meta.source = "benchmark"`.

Эти события предназначены только для технической проверки событийного контура. Их не следует интерпретировать как реальные пользовательские действия.

## 8. Ограничения интерпретации

Результаты бенчмарка являются локальной dev-оценкой. Они зависят от характеристик компьютера, Docker/локального запуска, версии Node.js, состояния PostgreSQL и ClickHouse, числа уже накопленных событий и фоновой нагрузки.

Поэтому результаты корректно использовать как:

1. подтверждение работоспособности API под контролируемой нагрузкой;
2. сравнительную оценку разных endpoint внутри одного стенда;
3. иллюстрацию влияния `batchSize` на событийный endpoint;
4. материал для раздела диплома об оценке качества разработанного решения.

Некорректно трактовать эти числа как production SLA или как гарантию поведения платформы на другой инфраструктуре.
